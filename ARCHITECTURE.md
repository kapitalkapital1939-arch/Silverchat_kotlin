# Архитектура SilverChat

Нативное Android-приложение: Kotlin, Jetpack Compose, Gradle. Никакого
веб-кода — ни HTML, ни CSS, ни JavaScript. Серверная часть существует в виде
контракта в [backend-contract/](backend-contract/README.md).

Масштаб на момент описания: **22 модуля**, **214 файлов Kotlin**, около
**51 000 строк**. Четыре из этих файлов — тесты (67 проверок); покрытие
ограничено нижним уровнем пирамиды, см. «Тестирование» и «Известные пробелы».

## Принципы

### 1. Зависимости направлены внутрь, к бизнес-логике

`:core:domain` знает только о моделях и не знает ни об Android, ни о Retrofit,
ни о Room. Всё внешнее — реализации, которые подключаются к нему через
интерфейсы. Практический смысл: use case можно запустить в обычном JUnit-тесте
без Robolectric и эмулятора.

### 2. Фичи не знают друг о друге

`:feature:market` не может перейти в `:feature:profile` напрямую — только
через маршрут, объявленный в `:core:designsystem`. Иначе добавление фичи
требовало бы правки всех существующих, а удаление становилось невозможным.

### 3. Один источник правды на каждое решение

Версии — в `gradle/libs.versions.toml`. Настройки Android — в
`build-logic/convention/AndroidConfig.kt`. Адреса бэкенда — там же, в
`BuildConfig`. Имена заголовков — в `HttpHeaders`. Словарь операций протокола —
в `SocketOps`. Дублирование значения в двух местах означает, что рано или
поздно они разойдутся.

### 4. Offline-first как поведение по умолчанию, а не как режим

Данные из Room показываются сразу, сеть их уточняет. Отсутствие соединения —
нормальное состояние мобильного приложения, а не исключительная ситуация,
поэтому очередь отправки, оптимистичная запись и откат встроены в основную
логику, а не добавлены сбоку.

### 5. Ошибка — значение, а не исключение

Публичные операции возвращают `ScResult<T>`. Исключения остаются внутри слоя
данных. UI не может забыть `try/catch`, потому что его нет: необработанный
результат не компилируется, когда `when` обязан покрыть все варианты.

### Правило слоёв, нарушать которое нельзя

**`:core:network` не зависит от `:core:domain`.**

Соблазн велик: мапперам из DTO в доменную модель нужны обе стороны. Но если
сетевой слой узнает о домене, он перестанет быть заменяемым, а домен окажется
связан с конкретной схемой обмена. Мапперы живут в `:core:data` — единственном
модуле, который знает и о DTO, и о доменных моделях.

**Фичи не зависят от `:core:data`.**

Экран получает use case из `:core:domain` через Hilt. Реализация подставляется
в `:app`. Благодаря этому фичу можно собрать с подставным репозиторием —
именно так работают превью и UI-тесты.

## Сквозные сценарии

### Отправка сообщения

```
UI (поле ввода)
  → SendMessageUseCase                     :core:domain   — валидация длины, прав
    → MessageRepository.send(…)            :core:domain   — интерфейс
      → MessageRepositoryImpl              :core:data
        ├─ 1. Room: запись со статусом PENDING и client_message_id
        ├─ 2. Flow<Message> уже отдаёт её в UI — сообщение видно мгновенно
        ├─ 3. RealtimeSocket.send("message.send", …)   :core:network
        │      сокет недоступен → OutgoingQueue, отправка после переподключения
        └─ 4. По ack: Room обновляется серверным id и статусом SENT
             По error: статус FAILED, UI предлагает повтор
```

Порядок шагов 1–2 до шага 3 принципиален: запись в локальную базу **до**
отправки на сервер и есть оптимистичная запись. Обратный порядок дал бы
задержку, заметную на каждой отправке, и пустой экран при офлайне.

### Входящее сообщение

```
RealtimeSocket.frames (SharedFlow)         :core:network
  → RealtimeBus / RealtimeDispatcher       :core:data
    → SocketEventDecoder → SocketEvent.MessageNew
      → Room: вставка сообщения
      → ChatDao.observe…  →  Flow в ViewModel  →  recomposition
```

UI не подписан на сокет. Он наблюдает за Room, а сокет пишет в Room. Одно
следствие: сообщение появляется в интерфейсе ровно один раз, даже если
событие пришло и по сокету, и по инкрементальной синхронизации.

### Куда попадает событие: Room или шина

`RealtimeDispatcher` решает это по одному признаку — **есть ли у данных
локальное хранилище**.

Есть — событие пишется в DAO и доходит до интерфейса через обычный `Flow` из
Room: сообщения, чаты, черновики, сторис, журнал кошелька. Шина в этом не
участвует, иначе получилось бы два канала доставки одного и того же, и запись
пришла бы дважды.

Нет — событие уходит в `RealtimeBus`: сигналинг звонков, «печатает…», список
ICE-серверов, пуш баланса. Это мгновенные состояния, которые бессмысленно
кэшировать: через секунду они уже неверны, а `SharedFlow` с `DROP_OLDEST`
гарантирует, что медленный подписчик не остановит диспетчер.

`wallet.ledger.append` — пример того, как событие переходит из второй группы в
первую. Журнал кошелька хранится в Room, поэтому строка пишется в `LedgerDao`
напрямую; `upsert` по первичному ключу делает повторную доставку безопасной —
а она возможна, потому что сервер вправе повторно прислать строку после
переподключения.

### Звонится звонок

```
Push или call.incoming по сокету
  → NotificationFactory.buildIncomingCall  :core:notifications  — полноэкранное уведомление
  → тап по «Ответить» → PendingIntent → MainActivity → маршрут Routes.CALL
  → CallViewModel → WebRtcClient           :core:webrtc
      call.signal (offer/answer/candidate) через тот же сокет
  → медиа идёт напрямую между устройствами, сервер не участвует
```

### Покупка юзернейма

```
BuyUsernameUseCase                          :core:domain
  → MarketRepository.buy(…)
    → POST /v1/market/usernames/buy         :core:network
    → BuyResponse.toDomain() → PurchaseResult
        success | insufficient_funds | taken | reserved | forbidden
  → WalletRepository observes wallet.updated по сокету → новый баланс
```

Покупка отвечает `200 OK` со структурированным исходом, а не HTTP-ошибкой:
«не хватило сильверов» — нормальная ветка сценария, и интерфейс показывает
суммы, а не «ошибка».

## Offline-first

Три механизма, работающих вместе.

**Очередь исходящих кадров** (`OutgoingQueue`). Ограничена 500 кадрами:
бесконечная очередь при длительном офлайне — это нехватка памяти. Эфемерные
кадры («печатает…», присутствие, просмотр сторис) старше пяти минут
сбрасываются: они вводят в заблуждение, а не несут информацию.

**Дедупликация по `client_message_id`.** Идентификатор создаётся до отправки и
сохраняется в локальной БД. Повтор после переподключения уходит с тем же
идентификатором, сервер возвращает уже созданное сообщение.

**Инкрементальная синхронизация.** `GET /v1/chats?since=<server_time>`
возвращает только изменившееся. Метка времени — серверная, а не локальная:
неверные часы на устройстве не должны приводить к пропуску обновлений.

Откат оптимистичной записи выполняется событием `chat.updated`, а не отдельным
протоколом: сервер рассылает актуальное состояние, клиент перезаписывает
локальное. Один механизм синхронизации вместо двух.

**`InFlightGuard`** убирает дубли параллельных одинаковых запросов: если
несколько экранов одновременно запрашивают один профиль, в сеть уходит один
запрос, а результат получают все.

**Курсор догрузки хранится в кэше, а не отдельно.** Журнал кошелька
догружается страницами по `before=<id>`, и курсором служит идентификатор самой
старой записи в Room. Отдельное поле для курсора пришлось бы переживать смерть
процесса и могло бы разъехаться с таблицей; производный курсор разъехаться не
может по построению. Обратная сторона — кэш нельзя обрезать по размеру:
обрезка удаляет самые старые записи, то есть ровно те, на которые указывает
курсор, и догрузка начала бы возвращать их по кругу.

## Навигация

### Одна Activity

Весь интерфейс — Compose, переходы делает `NavController`. Отдельные Activity
для звонка или просмотра сторис дали бы пересоздание темы, потерю состояния
стекла и лишний уровень в стеке задач. Полноэкранные слои остаются маршрутами
того же графа — их определяет `NavigationTransitions.FULLSCREEN_ROUTES`
(`STORY_VIEWER`, `STORY_CREATE`, `CALL`).

### Реестр графов

Каждая фича объявляет `FeatureNavigation`:

```
route                      — корневой маршрут графа
topLevelDestination        — вкладка нижней навигации, если фича верхнего уровня
registerGraph(builder, navController)  — регистрация маршрутов
deepLinks()                — обрабатываемые ссылки
```

`:app` собирает их в `Set<FeatureNavigation>` одним `@Provides` в
`AppNavigationModule`. Реестр явный, а не через `@IntoSet`: состав и порядок
видны в одном месте. Добавление фичи — одна строка; `AppNavHost` при этом не
меняется.

`AppNavHost` регистрирует графы так:

```
features.forEach { feature -> with(feature) { registerGraph(navController) } }
```

`with(feature)` нужен, потому что `registerGraph` — функция-расширение для
`NavGraphBuilder` с двумя приёмниками. Все маршруты попадают в корневой граф,
вложенные `navigation { }` не используются.

### Нижняя навигация

Четыре вкладки в стиле Telegram: **чаты, маркет, настройки, профиль**
(`TopLevelDestination`). Подписи намеренно заданы в перечислении, а не в
`strings.xml`: они не переводятся, а лишняя строка в ресурсах при включённом
`UnusedResources` превращается в предупреждение, которое нужно сопровождать.

Переключение вкладок даёт поведение Telegram тремя флагами:
`popUpTo(startDestination) { saveState = true }` сохраняет стек вкладки,
`restoreState = true` возвращает прокрутку, `launchSingleTop = true` не
создаёт вторую копию экрана при повторном тапе.

Панель использует `glassSurface` с размытием, поэтому `containerColor` у
`Scaffold` прозрачный: под стеклом должно быть видно содержимое экрана.

### Смена авторизации

`startDestination` у `NavHost` читается один раз при создании графа, поэтому
значение фиксируется в `remember`, а вход и выход обрабатываются явным
переходом с очисткой стека (`popUpTo(startDestination) { inclusive = true }`).
Без `inclusive` после выхода «назад» вернул бы пользователя в список чатов
разлогиненной сессии.

Пока состояние авторизации не определено, граф не создаётся вовсе, а
системная заставка удерживается через `setKeepOnScreenCondition`. Для этого
`AppUiState.isLoggedIn` трёхзначный (`Boolean?`): отличие «ещё не знаем» от
«не вошёл» убирает вспышку экрана входа у авторизованного пользователя.

### Переходы извне

`AppDeepLink` — запечатанный тип из двух вариантов: `Route(String)` для
внутренних маршрутов и `UriLink(Uri)` для публичных ссылок `silverchat://…`.
Тап по уведомлению даёт `Route`, ссылка из браузера — `UriLink`, который
сопоставляет сам `NavController` по спецификациям из графов фич.

## Внедрение зависимостей

Hilt. Стиль модулей единый: `object` с `@Provides` и отдельный
`abstract class` с `@Binds` в одном файле.

| Модуль | Что даёт |
|---|---|
| `NetworkModule` | `Json`, `OkHttpClient` (REST и WS раздельно), `Retrofit`, `SilverChatApi` |
| `DatabaseModule` | `SilverChatDatabase`, DAO |
| `DataStoreModule` | `SettingsDataStore`, привязка `SettingsRepository` |
| `SecurityModule` | `SecureStorage` на `EncryptedSharedPreferences`, `TokenStore` |
| `DataModule` | Привязки 12 реализаций репозиториев к интерфейсам |
| `ApplicationScopeModule` | `@ApplicationScope CoroutineScope` — `SupervisorJob` + `Dispatchers.Default` |
| `AppBindsModule` | `MediaCaptureGateway`, `ProfileMediaPicker` |
| `AppNavigationModule` | `Set<FeatureNavigation>` |

`@ApplicationScope` нужен для работы, переживающей экран: жизненный цикл
WebSocket-сессии, показ админ-рассылок, отправка inline-ответа из
уведомления. `viewModelScope` для этого не годится — он умирает с экраном.

### Жизненный цикл сессии

`SessionLifecycle` подписан на `TokenStore.authState`, но сравнивает **только
идентификатор пользователя**, а не состояние целиком:

```
authState → (Authenticated)?.userId → distinctUntilChanged()
    null      → disconnect()
    userId    → connect()
```

`AuthState.Authenticated` — data-класс, содержащий токен. Сравнение по всему
объекту привело бы к переподключению сокета на каждое обновление токена, то
есть к разрыву соединения каждые 15 минут.

## Медиа-мост

Выбор файла, съёмка и запрос разрешений в Android возможны только из
`Activity`, а репозитории — синглтоны. Прямая зависимость означала бы, что
слой данных знает про `Activity`.

Решение — три слоя:

```
MediaCaptureGateway (:core:domain)   интерфейс: «дай мне фото»
        ▲
        │ реализация
ActivityCaptureGateway (:app)        через держатель находит Activity
        │
        ▼
ActivityResultBridgeHolder (:app)    @Singleton, attach/detach, эксклюзив
        │
        ▼
MainActivity : ActivityResultBridge  6 лаунчеров, CompletableDeferred
```

`MainActivity` публикует себя в держателе в `onStart` и снимает в `onStop`,
поэтому синглтон никогда не обращается к мёртвой Activity. В `onDestroy` все
ожидания завершаются — иначе корутина в слое данных осталась бы висеть на
`await()` навсегда.

Лаунчеры регистрируются в **инициализаторах полей**, а не в `onCreate`:
`registerForActivityResult` разрешено вызывать только до перехода в `STARTED`,
а инициализатор поля выполняется в конструкторе и гарантированно успевает.

CameraX в проекте нет намеренно. Съёмка делегируется системному приложению
камеры через `TakePicture` и `CaptureVideo` — это экономит зависимости и даёт
пользователю привычный интерфейс камеры производителя. Грант на
`content://`-URI выдаётся всем пакетам, способным снять фото: без него
сторонняя камера не сможет записать файл в наш кэш и молча вернётся пустой.

## Дизайн-система

### Glassmorphism

Стеклянные поверхности (`glass/GlassSurface.kt`) используют размытие фона.
Единственное `GlassState` создаётся в корне и передаётся вниз, чтобы все
слои стекла в пределах экрана были согласованы.

### Тема

`SilverChatTheme(theme, fontScale, animations)` оборачивает всё приложение
снаружи `Scaffold`, поэтому масштаб шрифта и отключение анимаций действуют и
на нижнюю панель, и на любой экран фичи. Смена темы в настройках перерисовывает
приложение целиком, без перезапуска Activity.

Отключение анимаций — не косметика: это требование доступности, и оно
пробрасывается в `NavigationTransitions`, где каждая из четырёх функций
перехода принимает флаг `animationsEnabled`.

### Изображения

Coil 3 со стандартным загрузчиком. Кастомный `ImageLoader`, разделяющий
`OkHttpClient` с REST-запросами, **не** создаётся — осознанно: медиа отдаётся
по публичным и подписанным URL, заголовок авторизации им не нужен, а выигрыш
свёлся бы к переиспользованию пула соединений. Если CDN начнёт требовать
авторизацию, общий клиент станет необходимым — место для него
`SilverChatApplication`.

## Уведомления

Каналы создаются при старте приложения (`NotificationChannelSetup`). На
Android 8+ уведомление в несозданный канал не показывается вовсе, поэтому
пропуск этого шага означал бы молча пропущенные звонки.

Inline-ответ из уведомления реализован по-настоящему, через `RemoteInput`:

```
NotificationFactory.buildReplyAction(chatId)
  → RemoteInput.Builder(KEY_REMOTE_INPUT) + setAllowGeneratedReplies(true)
  → PendingIntent.getBroadcast(…)        не Activity!
    → ReplyReceiver (@AndroidEntryPoint, объявлен в манифесте)
      → goAsync() + запуск в @ApplicationScope
        → MessageRepository.send(ChatId, MessageContent.Text)
          → при успехе notifications.cancelGroup(chatId)
```

Широковещательный `PendingIntent`, а не запуск Activity: ответ из уведомления
не должен открывать приложение и пересоздавать весь интерфейс. `goAsync()`
даёт приёмнику время на сетевой запрос — без него процесс был бы убит сразу
после `onReceive`.

Контракт между фабрикой и приёмником вынесен в публичный объект
`DirectReplyContract` (`ACTION`, `KEY_CHAT_ID`, `KEY_REMOTE_INPUT`), поэтому
строки действий не дублируются и не могут разойтись.

## Безопасность на клиенте

| Что | Где |
|---|---|
| Токены, `device_id`, PIN блокировки | `EncryptedSharedPreferences`: мастер-ключ AES256-GCM в Keystore, ключи записей AES256-SIV, значения AES256-GCM |
| Обмен токенов при `401` | `TokenAuthenticator`, один повтор с меткой `X-SC-Token-Retry` |
| Пиннинг сертификатов | `NetworkModule`, значения из `BuildConfig.CERT_PINS` |
| Биометрия | Только `BIOMETRIC_STRONG` |
| Блокировка скриншотов | `FLAG_SECURE` по настройке |
| Логирование | `ScLogger` маскирует номера и токены; в release дерево Timber не сажается |

Сообщения и медиа в Room **не шифруются**. Это компромисс: шифрование базы
защищает только от физического извлечения, а стоит заметной просадки на
прокрутке истории. Компенсируется `allowBackup = false`, `FLAG_SECURE` и
размещением вложений в приватных каталогах приложения.

Подробности и серверная часть — в
[backend-contract/06-security.md](backend-contract/06-security.md).

## Обработка ошибок

`apiCall { }` в `:core:network` — обёртка над сетевым вызовом, которая
понимает HTTP-статусы и конверт ошибки сервера. До её появления все `4xx`/`5xx`
превращались в `ScError.Unknown`, потому что `Throwable.toScError()` в
`:core:common` разбирает только семейство `IOException`: интерфейс не отличал
«юзернейм занят» от «сервер упал», а `InsufficientFunds` и `PremiumRequired`
не возникали из сети вовсе.

`:core:common` не знает про Retrofit, поэтому отображение добавлено в
`:core:network`, а все 12 репозиториев используют `apiCall` вместо `scResult` —
134 места вызова, из них 118 обычных и 16 идемпотентных (см. следующий раздел).

Отмена корутины пробрасывается, а не оборачивается: проглотить
`CancellationException` — значит сломать structured concurrency.
`ScError.Canceled` при этом существует как отдельный вариант и никогда не
показывается пользователю.

Полная таксономия — в [backend-contract/07-errors.md](backend-contract/07-errors.md).

## Идемпотентность денежных операций

Шестнадцать операций двигают серебро или создают оплаченную сущность. Каждая
уходит с заголовком `Idempotency-Key`, иначе обрыв связи после списания
превращается в двойное списание: сервер работу выполнил, ответ потерялся,
пользователь нажал «Повторить».

### Ключ создаёт репозиторий, а не интерцептор

Интерцептор видел бы один `Call` и мог бы сгенерировать только новый ключ на
каждый запрос. Опасный сценарий происходит **между** вызовами, а второй вызов —
это новый `Call`, и интерцептор дал бы ему новый ключ. Защита не сработала бы
ровно там, где нужна.

Решение о том, считать ли повтор тем же намерением, принимает слой, знающий
контекст операции. Поэтому ключ живёт в `IdempotencyKeyStore` (`:core:data`),
а не в сетевом слое.

### Две стратегии — и почему их именно две

| | Операция поглощает цель | Операцию законно повторить |
|---|---|---|
| Примеры | покупка лота, принятие оффера, конвертация подарка, стрик, Premium | перевод, подарок, оффер, своп, продажа, админские начисления |
| Ключ | стабильный, 10 минут, до определённого исхода | новый на каждый вызов |
| Ручной «Повторить» после таймаута | уходит с **тем же** ключом | уходит с новым |
| Защита от потерянного ответа | `IdempotencyKeyStore` | автоматический повтор внутри вызова |

Купить один и тот же лот дважды нельзя — значит повтор в коротком окне может
быть только ретраем. Перевести одну и ту же сумму одному и тому же человеку
дважды — можно, и стабильный ключ молча проглотил бы второй перевод. Одна
стратегия на все операции в любом из вариантов давала бы либо двойное
списание, либо потерянное действие.

В админ-панели ключ всегда новый осознанно: тихий no-op там хуже двойного
списания, потому что его невозможно отличить от поломки.

### `apiCallIdempotent`

Повторяет вызов при **неопределённом исходе** — `ScError.Network` и
`ScError.Server`. Ключ создаётся до вызова и захватывается замыканием, поэтому
обе попытки уходят с одним значением.

Определённые ответы не повторяются: `409`, `InsufficientFunds` и `Validation`
означают, что действие не выполнено, а `RateLimited` обрабатывается паузой в
интерфейсе — автоматический повтор при `429` превратился бы в лавину.

Побочные эффекты стоят **вне** повторяемого блока: `claimDailyStreak` обновляет
журнал кошелька в `onSuccess`, а не внутри `apiCallIdempotent`, иначе ретрай
обновил бы его дважды.

### Сброс при смене аккаунта

Хранилище — синглтон, поэтому без сброса ключ покупки предыдущего пользователя
дожил бы до следующего входа. Сброс стоит в `SyncRepositoryImpl.disconnect()`,
куда сходятся оба пути завершения сессии: явный выход (`LogoutUseCase`) и
принудительный (`SessionLifecycle` по `session.kick` или провалу refresh).
Размещение в `:app` было бы невозможно — хранилище `internal` для `:core:data`.

Это второй рубеж: первый — серверная привязка ключа к `user_id`.

Нормативное описание — в
[backend-contract/02-rest-api.md](backend-contract/02-rest-api.md), раздел
«Идемпотентность».

## Качество кода

| Инструмент | Статус | Конфигурация |
|---|---|---|
| ktlint | **блокирует CI** | `.editorconfig`: стиль `android_studio`, лимит 140 символов |
| Android Lint | **блокирует CI по `severity=error`** | `config/lint/lint.xml` |
| detekt | отчёт, не блокирует | `config/detekt/detekt.yml` |

### Почему `warningsAsErrors` выключен

Android Lint выдаёт предупреждение `GradleDependency` всякий раз, когда
доступна более новая версия библиотеки. При `warningsAsErrors = true` CI
становился бы красным через неделю после любого релиза AndroidX, не имея
отношения к коду. Вместо этого нужный набор проверок поднят до
`severity = error` явным списком в `lint.xml` — его можно пересматривать
построчно, а не «всё подряд».

### Почему detekt пока не блокирует

Проект использует detekt `2.0.0-alpha.6`. Ветка 1.23.x собрана против Kotlin
2.0.21 и на Kotlin 2.3 даёт ложные срабатывания вплоть до внутренних ошибок
анализатора, поэтому выбрана 2.0, построенная на Kotlin 2.4.10 и знакомая с
AGP 9.3. Но это альфа, и стабильность состава правил между альфами не
гарантирована. Пороги сложности в `detekt.yml` выставлены по измеренным
максимумам кодовой базы, а не выдуманы.

Включение блокировки — два шага: `./gradlew detektBaseline`, затем
`ignoreFailures = false` в `silverchat.quality.gradle.kts`.

### Лимиты сложности измерены, а не назначены

| Метрика | Максимум в коде | Порог в detekt |
|---|---|---|
| Длина функции | 225 строк (`MarketScreen`, `@Composable`) | 80 + `ignoreAnnotated: ['Composable']` |
| Число параметров | 18 (фикстуры в `:core:testing`) | 20 |
| Функций в файле | 148 (`SilverChatApi` — интерфейс REST) | 160 |
| Длина строки | 140 символов | 140, совпадает с `.editorconfig` |

`SilverChatApi` — 148 объявлений эндпоинтов в одном интерфейсе, и это
осознанно: разбивка лишила бы проект единой точки, где виден весь контракт с
бэкендом. Compose-экраны исключены из правила о длине метода, потому что
декларативное дерево из 200 строк читается легче, чем 60 строк императивного
кода.

## Тестирование

`:core:testing` даёт фикстуры (`aUser`, `aMessage`, `aChat`, `aWallet`,
`masterAccount`, …), `MainDispatcherRule` и `TestDispatcherProvider`, который
сводит все диспетчеры приложения к одному `TestDispatcher`. Значения по
умолчанию у фикстур намеренны: тест, проверяющий одно поле, не обязан
перечислять остальные двадцать. От расхождения фикстуры с моделью защищает не
отсутствие значений по умолчанию, а компилятор — при удалении или
переименовании поля фикстура перестаёт собираться.

| Уровень | Чем | Где |
|---|---|---|
| Маппинг ошибок, декодер WebSocket, идемпотентность | JUnit + Truth, без Android | `:core:common`, `:core:network`, `:core:data` |
| Use case'ы | JUnit, без Android | `:core:domain` |
| Репозитории | MockK + фикстуры | `:core:data` |
| ViewModel | Turbine для `Flow` | `:feature:*` |
| Compose | `androidx.compose.ui.test` | `:feature:*` |
| Сквозные | Espresso, Hilt-тесты | `:app` |

CI собирает и прогоняет тесты по группам модулей (`core`, `feature`, `app`)
параллельно; зависимости для всех уровней подключены ко всем модулям через
convention-плагины, поэтому новый тест не требует правки `build.gradle.kts`.

### Что покрыто

67 тестов в четырёх файлах — там, где ошибка молчалива и стоит денег или
данных, то есть там, где её не ловят ни компилятор, ни типы:

| Файл | Тестов | Что защищает |
|---|---|---|
| `ScErrorMappingTest` (`:core:common`) | 16 | Порядок ветвей `toScError()`: `SocketTimeoutException`, `UnknownHostException` и `SSLException` обязаны разбираться раньше `IOException`. Сохранение `cause`, распаковка `ScException`, правило «`CancellationException` не заворачивается». Комбинаторы `scResult`, `map`, `onSuccess`, `onFailure`, `getOrNull`, `getOrThrow` |
| `ApiCallTest` (`:core:network`) | 28 | Разбор каждого HTTP-статуса в свой `ScError`, приоритет бизнес-кода над статусом, перенос `Retry-After` из секунд в миллисекунды, устойчивость к битому, пустому и неполному телу ошибки, `apiCall`/`apiCallIdempotent`/`isUnknownOutcome` |
| `SocketEventDecoderTest` (`:core:network`) | 11 | Известный кадр → свой тип с сохранением полей; неизвестный `op` → `Unknown`, а не падение; битая или неполная нагрузка → `DecodeFailure`, а не разрыв подписки; лишние поля сервера игнорируются |
| `IdempotencyKeyStoreTest` (`:core:data`) | 12 | Одно намерение — один ключ, в том числе под 32 одновременными потоками; `forget` и `reset`; уникальность `freshKey()`; клиентское окно TTL короче серверного срока хранения |

Первые два файла — регрессионные: они защищают реальные дефекты, найденные при
написании тестов. `toScError()` в `ScResult.kt` и `toUploadError()` в
`MediaUploader.kt` разбирали `is IOException` раньше собственных подклассов
`IOException`, из-за чего три ветви были недостижимы: пользователь видел «Нет
соединения» вместо внятной причины — таймаута, несуществующего домена или
проблемы с сертификатом. Компилятор такого не предупреждает: порядок ветвей
`when` по типу формально корректен.

### Чего нет

Покрыт только нижний уровень пирамиды и только в четырёх точках. Use case'ы,
репозитории, ViewModel и Compose-экраны тестов не имеют — инфраструктура для
них готова, сами тесты не написаны. Это осознанный пробел, а не недосмотр:
см. «Известные пробелы».
