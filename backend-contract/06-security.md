# 06. Безопасность

## Транспорт

### Только TLS

`https://` и `wss://` без исключений. Клиент не содержит кода, который
позволял бы переключиться на незащищённый транспорт: `BACKEND_URL` и
`WS_URL` зашиты в `BuildConfig` на этапе сборки, а не читаются из настроек.
Отладочный трафик перехватывается прокси на устройстве разработчика, а не
отключением TLS в приложении.

`network_security_config` не ослабляет политику: пользовательские CA
разрешены только для debug-сборки.

### Certificate pinning

Пины подставляются на этапе сборки из одного источника
(`build-logic/convention/src/main/kotlin/AndroidConfig.kt` → `certPins()`):

| Источник | Переменная |
|---|---|
| CI | `SILVERCHAT_CERT_PINS` |
| Локальная сборка | `silverchat.certPins` в `gradle.properties` |

Формат: пины через запятую, каждый `sha256/<base64>`.

**Пинов должно быть минимум два** — основной и резервный ключ. С одним пином
ротация сертификата отключает все установленные приложения разом, и исправить
это можно только новым релизом, который пользователи ещё должны обновить.

Если значение пустое, пиннинг **не применяется вовсе**. Это осознанное
поведение, а не упущение: заглушка вместо настоящего пина делает
release-сборку нерабочей — OkHttp отклоняет каждый ответ с
`SSLPeerUnverifiedException`, а пользователь видит бесконечное «Нет
соединения» без внятной причины. Диагноз на чужом устройстве в таком случае
практически невозможен.

Пиннуется хост `api.silver.chat` (`HttpHeaders.PINNED_HOST`). Он обязан
совпадать с хостом из `BACKEND_URL`: OkHttp сверяет пин с именем хоста
запроса, и расхождение молча отключило бы защиту.

## Аутентификация

### Вход по номеру телефона

```
POST /v1/auth/otp/send    { "phone": "+37360123456", "device_id": "…" }
                     ←    { "phone": "…", "expires_in": 300, "retry_after": 60, "is_new_user": true }
POST /v1/auth/otp/verify  { "phone": "…", "code": "12345", "device_name": "Pixel 9" }
                     ←    AuthResponse
```

`AuthResponse`:

```json
{
  "access_token": "…",
  "refresh_token": "…",
  "expires_in": 900,
  "user": { },
  "session_id": "s_1",
  "ws_url": "wss://api.silver.chat/v1/realtime"
}
```

Требования к серверу:

- **`retry_after` обязателен.** Без него клиент может долбить `otp/send` и
  либо получить отказ без объяснения, либо израсходовать лимит пользователя.
  Клиент показывает обратный отсчёт.
- **`is_new_user`** определяет, куда вести пользователя после входа: в
  регистрацию профиля или сразу в список чатов. Определять это на клиенте по
  пустоте профиля нельзя — пустой профиль бывает и у существующего
  пользователя.
- **`expires_in`** — секунды жизни access-токена. Клиент не вычисляет срок
  сам и не зашивает его: значение приходит от сервера.
- **`ws_url`** позволяет серверу направить клиента на конкретный узел
  реального времени. Если поле `null`, клиент использует `BuildConfig.WS_URL`.

### Ограничение частоты OTP

Три уровня, все на сервере:

| Уровень | Порог | Ответ |
|---|---|---|
| На номер | 5 кодов в час | `429` с `retry_after_ms` |
| На устройство (`device_id`) | 10 запросов в час | `429` |
| На IP | 30 запросов в час | `429` |

Проверка по номеру обязательна: перебор OTP — это захват чужого аккаунта, а
не спам. Код обязан быть не короче 5 цифр и одноразовым; после 5 неверных
вводов код инвалидируется.

`device_id` приходит от клиента и не является доверенным — его можно
подделать. Он годится для эвристики и для отображения «активных сессий», но
не как единственный фактор.

### Ротация токенов

Access-токен короткоживущий, refresh-токен — долгоживущий и **одноразовый**:
при каждом `POST /v1/auth/refresh` сервер выдаёт новую пару, а старый
refresh-токен инвалидирует.

Клиент реализовал ротацию через `TokenAuthenticator` (OkHttp `Authenticator`):

1. Любой ответ `401` запускает обмен токенов.
2. Исходный запрос повторяется с новым access-токеном.
3. Повтор помечается заголовком `X-SC-Token-Retry: 1`; второй `401` на том же
   запросе означает, что обмен не помог, и клиент выходит из аккаунта.

Метка нужна против бесконечного цикла: без неё протухший refresh-токен
заставил бы клиент обменивать токены на каждый запрос навсегда.

**Требование к серверу:** заголовок `X-SC-Token-Retry` не несёт смысла для
бизнес-логики и должен игнорироваться. Полагаться на него в проверках нельзя
— клиент может его подделать.

**Повторное использование refresh-токена — признак компрометации.** Если
сервер видит запрос с уже израсходованным refresh-токеном, он обязан
инвалидировать всю цепочку сессии и отправить `session.kick` на активные
сокеты. Молчаливый отказ `401` оставил бы атаку незамеченной.

### Отзыв сессии

| Событие | Действие сервера |
|---|---|
| `POST /v1/auth/logout` | Инвалидирует refresh-токен текущей сессии |
| `DELETE /v1/auth/sessions/{id}` | Инвалидирует указанную сессию и отправляет ей `session.kick` |
| Бан пользователя | Инвалидирует все сессии, `session.kick` на все сокеты |
| Вход с нового устройства | Не рвёт старые сессии: мессенджер мультиплатформенный |

## Хранение на устройстве

### EncryptedSharedPreferences

Все секреты — в одном зашифрованном файле
(`core/security/EncryptedSecureStorage.kt`):

| Слой | Схема |
|---|---|
| Мастер-ключ | AES256-GCM, генерируется внутри Android Keystore, неизвлекаем |
| Ключи записей | AES256-SIV |
| Значения записей | AES256-GCM |

Файл: `silverchat_secure_prefs`. Мастер-ключ не покидает Keystore, поэтому
копия `shared_prefs` с другого устройства или из резервной копии бесполезна.

Хранимые ключи:

| Ключ | Содержимое |
|---|---|
| `sc_user_id` | Идентификатор пользователя |
| `sc_access_token` | Access-токен |
| `sc_refresh_token` | Refresh-токен |
| `sc_device_id` | Стабильный идентификатор устройства |
| `sc_session_id` | Идентификатор текущей сессии |
| `sc_app_lock_hash` | Хеш PIN-кода блокировки |
| `sc_biometric_enabled` | Включена ли биометрия |
| `sc_notif_content` | Показывать текст сообщений в уведомлениях |
| `sc_secure_flag` | Блокировать скриншоты и превью в списке задач |
| `sc_turn_cred_cache` | Кэш учётных данных TURN |
| `sc_admin_session_pin` | PIN админ-сессии `@silver` |

**`allowBackup` обязан быть `false`** для этого файла. Резервная копия
токенов в облаке — это их копия вне Keystore-защищённого устройства.

### Деградация вместо падения

Если Keystore недоступен (единичные кастомные прошивки, повреждённое
хранилище), приложение не падает на старте: файл пересоздаётся, а до этого
используется небезопасный режим в памяти с предупреждением в логе. Пользователю
предлагается войти заново. Выбор между «не запускается вовсе» и «запускается
с явной деградацией» сделан в пользу второго: первый вариант неотличим от
сломанного приложения.

### Что НЕ хранится в защищённом хранилище

Сообщения, чаты и медиа кэшируются в Room и в файловом кэше —
незашифрованными. Это осознанный компромисс: шифрование БД на каждом
устройстве даёт защиту только от физического извлечения, а стоимость —
заметная просадка на прокрутке истории. Компенсируется тремя мерами:

- `android:allowBackup="false"` — данные не уезжают в облако;
- `FLAG_SECURE` при включённой настройке — нет скриншотов и превью в списке
  задач;
- файлы-вложения живут в `cacheDir` и `filesDir` приложения, недоступных
  другим приложениям без root.

## Блокировка приложения

PIN хранится как хеш с индивидуальной солью
(`sc_app_lock_hash`), а не в открытом виде. Сравнение выполняется за
постоянное время (`constantTimeEquals`), чтобы по времени ответа нельзя было
подбирать символы.

Биометрия требует `BIOMETRIC_STRONG` — отпечаток или 3D-распознавание лица.
`BIOMETRIC_WEAK` (распознавание лица по обычной камере) не принимается: его
обходят фотографией.

Разблокировка выполняется **на устройстве и не заменяет токен**: access-токен
уже валиден, блокировка защищает от человека с чужим разблокированным
телефоном, а не от сервера.

## Звонки

Учётные данные TURN выдаются сервером на каждый звонок и живут не дольше часа:

```json
{ "urls": ["turn:turn.silver.chat:3478"], "username": "1730003600:u_7", "credential": "…" }
```

Постоянные учётные данные TURN превращают ретранслятор в открытый прокси —
через него можно гонять любой трафик за счёт владельца сервера. Формат
`username` = `<истечение>:<идентификатор>` позволяет серверу проверять срок
HMAC-подписью, не обращаясь к базе.

Сигналинг WebRTC идёт только через `call.signal` в авторизованном сокете.
Отдельного «комнаты-без-авторизации» нет: SDP-офер содержит медиаключи, и её
перехват позволяет расшифровать звонок.

## Админ-панель `@silver`

### Модель прав

Единственный источник прав — сервер. Клиент показывает админ-панель по флагу
`flags.is_master_account` и ответу `GET /v1/admin/access`, но **проверка на
каждом админ-запросе обязательна**: флаг в DTO — это подсказка для интерфейса,
а не разрешение.

| Действие | Эндпоинт |
|---|---|
| Выдать верификацию | `POST /v1/admin/users/{id}/verified` |
| Выдать Premium | `POST /v1/admin/users/{id}/premium` |
| Выдать статус разработчика | `POST /v1/admin/users/{id}/developer` |
| Назначить роль | `POST /v1/admin/users/{id}/role` |
| Начислить / списать сильверы | `POST /v1/admin/wallet/credit`, `…/debit` |
| Заблокировать / разблокировать | `POST /v1/admin/ban`, `…/unban` |
| Изъять юзернейм | `POST /v1/admin/usernames/{username}/block` |
| Изменить цену лота | `PATCH /v1/admin/listings/{id}/price` |
| Возврат операции | `POST /v1/admin/transactions/{id}/refund` |
| Рассылка | `POST /v1/admin/broadcast` |
| Изменить серверные лимиты | `PATCH /v1/settings` |

### Обязательный аудит

Каждое действие из таблицы пишется в журнал (`GET /v1/admin/audit`) и
рассылается подключённым администраторам событием `admin.log.append`. Запись
содержит: кто, кому, что, значение до и после, основание (`reason`), метку
времени, IP и идентификатор устройства.

Поле `reason` обязательно для начисления и списания сильверов: аккаунт
`@silver` может эмитировать валюту без ограничений, и единственная защита от
злоупотребления — неизменяемый журнал с внятным основанием. Журнал пишется в
таблицу без возможности `UPDATE` и `DELETE`.

### Безлимитный баланс

Мастер-аккаунт не проверяется на достаточность средств. Это значит, что
ошибка в коде начисления не обнаружится сама: вместо отказа получится
отрицательный или астрономический баланс у пользователя. Поэтому все
админ-операции с кошельком обязаны иметь верхнюю границу на одно действие и
подтверждение при её превышении.

### Рассылки

`POST /v1/admin/broadcast` с `audience` (`all | premium | verified | …`)
рассылает событие `admin.broadcast` всем подходящим онлайн-клиентам. Клиент
показывает системное уведомление
(`app/notification/AdminBroadcastNotifier.kt`).

Идентификатор уведомления — хеш текста, поэтому повторная рассылка с тем же
текстом заменяет предыдущее уведомление, а не складывается с ним в стопку.
Серверу это не мешает, но дублировать рассылку всё равно не стоит.

## Приватность данных

### Телефонный номер

Возвращается только владельцу (`users/me`) и админ-панели. В публичном
профиле поля `phone` быть не должно: его наличие позволяет перебирать номера
и определять, зарегистрирован ли человек в SilverChat.

### Логирование

Клиентский логгер (`ScLogger`) маскирует номера телефонов и токены. В
release-сборке дерево Timber не сажается вовсе: тексты сообщений он пишет как
есть, и оставлять переписку в logcat на устройстве пользователя нельзя.

Серверные логи подчиняются тому же правилу: тело сообщений, OTP-коды и токены
в логи не пишутся. Логируется идентификатор сообщения, но не его содержимое.

### Содержимое уведомлений

Настройка `sc_notif_content` позволяет показывать в уведомлении только
«Новое сообщение» без текста и имени. Сервер обязан это учитывать: если
push-уведомление формируется на сервере и содержит текст, отключить его
клиентской настройкой уже нельзя.

Рекомендуемая схема — «тихие» push: сервер отправляет только сигнал о
появлении данных, а содержимое клиент подтягивает сам и формирует уведомление
локально. Это заодно решает проблему текста в логах push-провайдера.

## Чек-лист перед релизом

| # | Что проверить | Последствие пропуска |
|---|---|---|
| 1 | `SILVERCHAT_CERT_PINS` задан в секретах CI, минимум два пина | Release-сборка без пиннинга (CI предупредит) |
| 2 | `allowBackup = false` | Токены уезжают в облачную резервную копию |
| 3 | Refresh-токены одноразовые, повтор инвалидирует сессию | Украденный токен работает бесконечно |
| 4 | Лимиты OTP на номер, устройство и IP настроены | Перебор кодов и захват аккаунтов |
| 5 | Учётные данные TURN короткоживущие | Открытый прокси за счёт сервера |
| 6 | Каждый `/v1/admin/*` проверяет права сервером | Любой клиент с подделанным флагом получает админ-доступ |
| 7 | Журнал аудита пишется без возможности изменения | Злоупотребление `@silver` недоказуемо |
| 8 | `phone` не возвращается в чужом профиле | Enumeration пользователей по номерам |
| 9 | Тексты сообщений и коды не попадают в серверные логи | Утечка переписки через инфраструктуру |
