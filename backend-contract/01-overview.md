# 01. Обзор: адреса, транспорты, соглашения

## Два транспорта, одна модель данных

SilverChat использует два канала, и они решают разные задачи:

| | REST (HTTPS) | WebSocket (WSS) |
|---|---|---|
| Назначение | Команды и запросы с гарантированным ответом | События и состояние в реальном времени |
| Инициатор | Всегда клиент | Обычно сервер |
| Модель | Запрос → ответ, состояние не хранится | Долгоживущее соединение, двусторонний обмен |
| Что проходит | Авторизация, пагинация, поиск, покупки, загрузка медиа | Новые сообщения, печать, прочтение, сторис, сигналинг звонков, кошелёк |
| Ошибки | HTTP-статус + конверт ошибки | Кадр `error` + `ack` с флагом `ok` |

Правило разделения: **если клиенту нужен детерминированный ответ «сделано /
не сделано» — это REST. Если событие может прийти само, без запроса — это
WebSocket.** Отправка сообщения реализована в обоих каналах: REST — когда
сокет недоступен, WebSocket — в обычном режиме. Сервер обязан принимать оба
пути и давать одинаковый результат.

## Адреса

| Переменная | Значение | Комментарий |
|---|---|---|
| `BACKEND_URL` | `https://api.silver.chat/v1/` | Обязательно с завершающим `/`: Retrofit склеивает относительные пути (`chats`, `users/me`) без добавления слэша |
| `WS_URL` | `wss://api.silver.chat/v1/realtime` | Только `wss://`, незащищённый `ws://` запрещён |
| `CDN_URL` | `https://cdn.silver.chat/` | Отдача медиа; клиент кэширует через Coil |

Адреса зашиты в `BuildConfig` всех модулей из
`build-logic/convention/src/main/kotlin/AndroidConfig.kt`. Переопределение —
через переменные окружения CI или `gradle.properties`, не правкой кода.

## Версионирование

### REST
Версия в пути: `/v1/`. Изменение мажорной версии — новый префикс, старая
ветка поддерживается не менее одного цикла обновления клиентов.

### WebSocket
Версия протокола передаётся дважды, и оба места должны совпадать:

1. Заголовок рукопожатия `X-SC-Protocol: 1` — виден до установления сессии.
2. Поле `v` в каждом кадре — проверяется на каждом сообщении.

```json
{ "v": 1, "id": "…", "op": "…", "ts": 1730000000000, "payload": {} }
```

**Поведение сервера при несовпадении версии.** Если клиент прислал `v`,
которую сервер не поддерживает, сервер обязан отправить `session.auth.fail`
с кодом `protocol_version_unsupported` и закрыть соединение с кодом `1002`
(protocol error). Закрывать соединение без объяснения нельзя: клиент уйдёт в
бесконечный цикл переподключений и не покажет пользователю, что нужно
обновить приложение.

### Совместимость без смены версии

Протокол спроектирован так, чтобы большинство изменений версии не требовало:

- **Новое поле в модели** — клиент собран с `ignoreUnknownKeys = true`, лишнее
  поле игнорируется. Не breaking change.
- **Новая операция `op`** — неизвестный кадр попадает в `SocketEvent.Unknown`
  и не роняет декодер. Не breaking change.
- **Новый вид контента сообщения** — неизвестный `kind` декодируется в
  `MessageContentDto.Unknown` и отображается как «Сообщение не
  поддерживается вашей версией». Не breaking change.
- **Удаление или переименование поля/операции, изменение типа** — breaking
  change, требует подъёма `PROTOCOL_VERSION`.

## Соглашения JSON

Конфигурация сериализатора задана один раз, в `NetworkModule.provideJson()`,
и сервер обязан ей соответствовать.

| Параметр | Значение | Следствие для сервера |
|---|---|---|
| `ignoreUnknownKeys` | `true` | Можно добавлять поля без согласования |
| `explicitNulls` | `false` | Клиент не отправляет поля со значением `null`: их отсутствие означает «не менять» |
| `coerceInputValues` | `true` | `null` в поле с non-null типом и значением по умолчанию принимается как default |
| `encodeDefaults` | `true` | Клиент отправляет значения по умолчанию явно; сервер не должен полагаться на отсутствие поля как на сигнал |
| `isLenient` | `false` | Некорректный JSON — ошибка, не «попытаться угадать» |
| `classDiscriminator` | `kind` | Полиморфные модели различаются полем `kind` |

### Именование полей

`snake_case` везде и всегда. Каждое поле в клиентских DTO помечено
`@SerialName`, поэтому соответствие жёсткое: `unread_count`, а не `unreadCount`.

### Время

Все временные метки — **миллисекунды epoch UTC**, целое число (`Long`).
Строки вида `2026-09-08T12:00:00Z` не используются: их разбор на клиенте
дороже, а часовые пояса — источник ошибок при отображении «5 минут назад».

### Идентификаторы

Строки. Сервер волен выбирать формат (UUID v7 рекомендуется: сортируем по
времени, что полезно для курсорной пагинации), но клиент трактует их как
непрозрачные значения и никогда не разбирает на части.

### Деньги и экономика

Баланс сильверов, цены и суммы операций — **целые числа**. Дробные денежные
типы запрещены: ошибка округления в экономике приводит к появлению или
исчезновению валюты. Если нужна доля — она выражается в минимальных единицах.

## Дисриминатор `kind`

Поле `kind` используется как дискриминатор полиморфных моделей. Значения
для контента сообщения:

```
text | photo | video | voice | circle | file | sticker | gif
     | location | contact | poll | service | gift
```

Неизвестное значение не является ошибкой — см. раздел о совместимости выше.

## Заголовки

Все имена собраны в одном словаре на клиенте —
`core/network/src/main/kotlin/com/silverchat/core/network/HttpHeaders.kt`.
Его используют и `AuthInterceptor` (каждый REST-запрос), и
`OkHttpRealtimeSocket` (рукопожатие WebSocket), поэтому расхождение имён
между двумя каналами исключено.

| Заголовок | Где отправляется | Значение |
|---|---|---|
| `Authorization` | REST (кроме `auth/*`) и WS-рукопожатие | `Bearer <access_token>` |
| `X-SC-Protocol` | REST и WS-рукопожатие | Версия протокола, `1` |
| `X-SC-Platform` | REST и WS-рукопожатие | `android` |
| `X-SC-App-Version` | REST | `APP_VERSION_NAME` |
| `Accept` | REST | `application/json` |
| `Accept-Language` | REST | `ru` — интерфейс существует только на русском |
| `Idempotency-Key` | POST с финансовым побочным эффектом | См. раздел «Идемпотентность» |
| `Retry-After` | Ответ сервера на `429` | Секунды, как требует RFC 9110 |
| `X-SC-Device-Id` | Зарезервирован | Стабильный идентификатор установки |

Публичные эндпоинты (`auth/otp/*`, `auth/refresh`) отправляются без
`Authorization`: токена на этом шаге ещё нет, а `AuthInterceptor` определяет
их по префиксу пути `/v1/auth/`.

`X-SC-Device-Id` в REST-запросах зарезервирован, но клиентом пока не
отправляется: идентификатор устройства сейчас уходит в рукопожатии
WebSocket полем `device_id` в `AuthPayload`. Если серверу понадобится
связывать REST-запросы с устройством (например, для антифрода OTP), поле
нужно включить в `AuthInterceptor` — значение берётся из `DeviceIdentity`.

### Токен не в query-строке

Access-токен передаётся **только** в заголовке `Authorization`. Передача в
query-параметре запрещена даже для WebSocket: URL попадает в логи
прокси-серверов, балансировщиков и CDN, а оттуда его не отозвать.

### Идемпотентность

Операции, двигающие серебро или создающие оплаченную сущность, обязаны
принимать заголовок `Idempotency-Key`. Сервер хранит соответствие ключа
результату не менее 24 часов и при повторе возвращает **первоначальный**
ответ, не выполняя действие второй раз.

**Область действия ключа — учётная запись, а не приложение.** Сервер обязан
хранить соответствие `(<user_id>, Idempotency-Key) → результат`. Ключ без
привязки к пользователю позволил бы одному участнику повторить чужой ключ и
получить чужой результат: UUIDv4 угадать нельзя, но утечка лога или
проксированного запроса превращает это в чтение чужой покупки.

Клиент со своей стороны сбрасывает несообщённые ключи при разрыве сессии
(`SyncRepository.disconnect()`), поэтому ключ предыдущего аккаунта не доживает
до следующего входа. Это второй рубеж, а не замена серверной привязки.

**Что делает клиент.** Заголовок посылают все 16 операций, двигающих серебро
или создающих оплаченную сущность; полный список — в
[02-rest-api.md](02-rest-api.md), раздел «Идемпотентность». Стратегий две, и
выбор между ними — содержательное решение, а не деталь реализации:

| Стратегия | Когда | Поведение |
|---|---|---|
| Стабильный ключ | Операция **поглощает цель**: покупка лота, принятие оффера, конвертация и улучшение подарка, получение стрика, покупка Premium | Ключ живёт до определённого исхода (10 минут), поэтому ручной «Повторить» после таймаута уходит с тем же значением |
| Новый ключ на вызов | Операцию **законно повторить**: перевод, подарок, оффер, своп, продажа, админские начисления | Ключ создаётся заново; от потерянного ответа страхует автоматический повтор внутри одного вызова |

Стабильный ключ во второй группе был бы ошибкой: он молча проглотил бы
намеренное второе действие, приняв его за ретрай. Для админ-панели тихий
no-op хуже двойного списания — его невозможно отличить от поломки.

Для отправки сообщений роль ключа играет `client_message_id`: он передаётся в
теле запроса и дедуплицируется на стороне сервера, поэтому отдельный заголовок
там не нужен — см. [03-websocket.md](03-websocket.md), раздел «Дедупликация».

## Таймауты клиента

Зафиксированы в `NetworkModule` и приведены здесь, потому что сервер должен
укладываться в них, а не наоборот.

| Таймаут | Значение | Комментарий |
|---|---|---|
| `connectTimeout` (REST) | 15 с | |
| `readTimeout` (REST) | 30 с | Обычные запросы обязаны отвечать быстрее |
| `writeTimeout` (REST) | 60 с | С запасом на загрузку медиа |
| `callTimeout` (REST) | 90 с | Полный цикл запроса |
| `readTimeout` (WS) | 0 | Отключён намеренно: сокет живёт, пока жив TCP |
| `writeTimeout` (WS) | 15 с | |
| `pingInterval` (WS) | 25 с | Протокольный ping OkHttp, страховка для NAT |

**Следствие для сервера.** Долгий REST-запрос (тяжёлая аналитика, массовая
выгрузка) упрётся в `readTimeout`. Такие операции нужно проектировать
асинхронно: быстрый ответ `202 Accepted` с идентификатором задачи, затем
опрос состояния или событие в WebSocket.
