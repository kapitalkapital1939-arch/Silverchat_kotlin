# 03. Протокол WebSocket

Реализация клиента: `core/network/src/main/kotlin/com/silverchat/core/network/ws/OkHttpRealtimeSocket.kt`.

## Конверт кадра

Каждое сообщение в обоих направлениях — один JSON-объект фиксированной формы.
Исключений нет: ни «голых» полезных нагрузок, ни текстовых команд.

```json
{
  "v": 1,
  "id": "9f2c1a4e-7b60-4d51-9c3a-2e8f0b71d654",
  "op": "message.new",
  "ts": 1730000000123,
  "payload": { }
}
```

| Поле | Тип | Обязательность | Смысл |
|---|---|---|---|
| `v` | int | Да | Версия протокола. Совпадает с `PROTOCOL_VERSION` |
| `id` | string | Да | Идентификатор кадра. Для команд — correlation id, для событий — идентификатор доставки |
| `op` | string | Да | Операция из словаря [04-events-catalog.md](04-events-catalog.md) |
| `ts` | long | Да | Миллисекунды epoch UTC. У клиента — момент отправки, у сервера — момент формирования |
| `payload` | object \| null | Нет | Полезная нагрузка. Отсутствует у кадров без данных |

**Бинарных кадров нет.** OkHttp-клиент принимает и текстовые, и бинарные
сообщения (`onMessage(ByteString)` декодируется как UTF-8), но сервер обязан
отправлять текст: бинарная экономия в несколько байт не окупает потери
читаемости при отладке через `wscat`.

### Идентификатор кадра

Генерируется отправителем как UUID. Для команды `id` — это correlation id:
сервер обязан вернуть его без изменений в `ack` и в ответном кадре, иначе
клиент не сможет сопоставить ответ с запросом. Сопоставление реализовано в
`sendAndAwait` через `ConcurrentHashMap<String, CancellableContinuation>`.

Для серверного события `id` используется как идентификатор доставки при
дедупликации: если сервер повторит событие после переподключения, клиент
сможет отбросить повтор.

## Рукопожатие

```
Клиент                                 Сервер
  │  HTTP Upgrade + заголовки            │
  │  Authorization: Bearer <token>       │
  │  X-SC-Protocol: 1                    │
  │  X-SC-Platform: android              │
  ├─────────────────────────────────────▶│
  │                                      │
  │  session.auth {token, device_id,     │
  │                protocol}             │
  ├─────────────────────────────────────▶│
  │                                      │
  │  session.auth.ok {session_id, …}     │
  │◀─────────────────────────────────────┤
  │                                      │
  │  session.subscribe {chat_ids: […]}   │
  ├─────────────────────────────────────▶│
  │                                      │
  │  chat.list.sync {chats, …}           │
  │◀─────────────────────────────────────┤
  │                                      │
  │  (кадры из очереди офлайн-отправки)  │
  ├─────────────────────────────────────▶│
```

Пошагово:

1. **HTTP Upgrade.** Токен передаётся заголовком `Authorization`, а не
   query-параметром: URL попадает в логи прокси и балансировщика, откуда его
   нельзя отозвать.

2. **`session.auth` — всегда первый кадр.** Полезная нагрузка:

```json
{ "token": "<access_token>", "device_id": "<session_id>", "protocol": 1 }
```

3. **До `session.auth.ok` клиент не отправляет ничего остального.** Команды,
   возникшие в это окно, буферизуются. Сервер, получивший команду до
   авторизации, обязан ответить `session.auth.fail`, а не игнорировать её
   молча.

4. **`session.auth.ok`** переводит клиента в `ConnectionState.Connected` и
   запускает heartbeat и сброс очереди.

5. **`session.auth.fail`** приводит к `tokenStore.onSessionInvalidated(...)` и
   разрыву соединения: повторные попытки с тем же токеном бессмысленны, нужен
   новый обмен токенов через REST.

6. **`session.subscribe`** — список идентификаторов чатов, которые интересуют
   клиента прямо сейчас:

```json
{ "chat_ids": ["c_1", "c_2"] }
```

Подписка нужна, чтобы сервер не рассылал события тысяч чатов клиенту, у
которого открыт один. Клиент повторяет подписку при смене открытого чата.

### `session.hello`

Операция объявлена в словаре, но клиентом не используется: он начинает диалог
сам. `session.hello` зарезервирован под сценарий, в котором сервер первым
сообщает параметры сессии (например, серверный интервал heartbeat или адрес
другого узла при миграции). Если сервер его отправит, клиент примет кадр как
`SocketEvent.Unknown` и проигнорирует — это не ошибка.

## Heartbeat

Работают **два** механизма, и это намеренно:

| Уровень | Кто отправляет | Интервал | Что проверяет |
|---|---|---|---|
| Протокольный WebSocket ping | OkHttp (`pingInterval`) | 25 с | Жив ли TCP-канал |
| Прикладной `session.ping` | `OkHttpRealtimeSocket` | 25 с (`WS_HEARTBEAT_SEC`) | Жив ли сервер как приложение, а не только сокет |

Протокольного ping недостаточно: он подтверждает, что TCP-соединение
существует, но не что серверный процесс обрабатывает кадры. Застрявший
цикл событий отвечает на ping на уровне ядра, а сообщения не обрабатывает.

Сервер обязан отвечать `session.pong` на каждый `session.ping`. Клиент считает
пропущенные ответы; после **двух** подряд (`MISSED_PONG_LIMIT`) соединение
считается мёртвым и инициируется переподключение.

Прикладной heartbeat нужен ещё и потому, что NAT у мобильных операторов
разрывает неактивные соединения через 30–60 секунд. Интервал 25 с выбран
меньше этого порога.

## Переподключение

Экспоненциальная задержка с дрожанием:

```
задержка = min(250 мс × 2^(попытка − 1), 30 000 мс) + random(0 … задержка/4)
```

| Попытка | Базовая задержка | С дрожанием |
|---|---|---|
| 1 | 250 мс | 250–312 мс |
| 2 | 500 мс | 500–625 мс |
| 3 | 1 000 мс | 1 000–1 250 мс |
| 4 | 2 000 мс | 2 000–2 500 мс |
| … | … | … |
| 8 и далее | 30 000 мс (потолок) | 30 000–37 500 мс |

**Дрожание обязательно.** Без него десять тысяч клиентов после короткого сбоя
подключаются одновременно и кладут только что поднявшийся сервер обратно —
классический thundering herd.

Счётчик попыток сбрасывается в ноль после успешной авторизации.

Во время переподключения клиент публикует состояние
`ConnectionState.Reconnecting(attempt, nextRetryInMs, reason)`, по которому
список чатов показывает баннер «Переподключение… попытка N».

### Единственность соединения

Все вызовы `connect()` идемпотентны: если состояние уже `Connecting` или
`Connected`, новый сокет не создаётся. Это защита от удвоения событий —
самой частой причины жалоб «сообщения приходят дважды».

**Требование к серверу:** повторное подключение того же `device_id` не должно
оставлять старую сессию живой. Иначе клиент, переподключившись, получает
события в оба сокета.

### Коды закрытия

| Код | Кто | Смысл | Действие клиента |
|---|---|---|---|
| `1000` | оба | Штатное закрытие | Не переподключается |
| `1001` | клиент | Приложение уходит в фон | Переподключается при возврате |
| `1002` | сервер | Ошибка протокола, в том числе неподдерживаемая версия | Переподключение бессмысленно |
| `1008` | сервер | Нарушение политики (бан, отзыв сессии) | Требуется повторный вход |
| `1011` | сервер | Внутренняя ошибка | Переподключение с backoff |

Отдельно: кадр `session.kick` означает, что сервер отозвал сессию (вход с
другого устройства, бан, истечение refresh-токена). Клиент вызывает
`tokenStore.onSessionInvalidated("session.kick")` и разрывает соединение —
пользователь возвращается на экран входа. Молча закрывать сокет без
`session.kick` нельзя: клиент будет переподключаться вечно.

## Correlation и подтверждение

Команда, отправленная через `sendAndAwait`, приостанавливает корутину до кадра
с тем же `id`. Сервер отвечает одним из двух способов:

**Успех — кадр `ack`:**

```json
{ "v": 1, "id": "<тот же id>", "op": "ack", "ts": 0,
  "payload": { "op": "message.send", "ok": true } }
```

**Ошибка — кадр `error`:**

```json
{ "v": 1, "id": "<тот же id>", "op": "error", "ts": 0,
  "payload": {
    "code": "chat_not_found",
    "message": "Чат не найден",
    "retryable": false
  }
}
```

Поле `payload.op` в `ack` обязательно: оно позволяет отличить подтверждение
команды от события, пришедшего по тому же идентификатору.

Если ответ не нужен, используется `send(op, payload)` — он возвращает `id`
сразу, не дожидаясь сервера. Так отправляются «печатает…» и просмотр сторис:
потеря такого кадра не важна, а ожидание ответа замедлило бы интерфейс.

## Очередь офлайн-отправки

`core/network/src/main/kotlin/com/silverchat/core/network/ws/OutgoingQueue.kt`.

| Параметр | Значение | Обоснование |
|---|---|---|
| Максимальный размер | 500 кадров | Бесконечная очередь при «вечном офлайне» — это OOM |
| Время жизни эфемерных кадров | 5 минут | «Печатает…» десятиминутной давности бессмысленно и вводит в заблуждение |
| Эфемерные операции | `message.typing`, `presence.update`, `session.ping`, `story.view` | Теряют смысл при задержке |

При переполнении сбрасывается **самый старый** кадр, а не новый: новое
сообщение важнее старого.

Очередь переживает только переподключения, не процесс. Неотправленные
сообщения дополнительно хранятся в Room, поэтому убийство приложения не
теряет текст.

### Дедупликация

Каждое исходящее сообщение несёт `client_message_id` — идентификатор,
созданный клиентом **до** отправки и сохраняемый вместе с сообщением в
локальной БД. При повторной отправке того же сообщения (после
переподключения, после ретрая) идентификатор не меняется.

Сервер обязан:

1. Хранить `client_message_id` в уникальном индексе по `(chat_id,
   client_message_id)`.
2. При повторе возвращать **уже созданное** сообщение с его серверным `id`, а
   не создавать второе.
3. Возвращать в ответе поле `client_message_id` без изменений — клиент
   сопоставляет по нему локальную оптимистичную запись с серверной.

Без этого каждое переподключение с неотправленными сообщениями давало бы
дубликаты в переписке.

## Состояние соединения

Клиент различает шесть состояний (`core/model/SocketEvent.kt` →
`ConnectionState`). Серверу они не передаются, но определяют поведение
интерфейса и очереди отправки.

| Состояние | Когда | Что видит пользователь |
|---|---|---|
| `Disconnected` | Сокет не создан | «Офлайн — сообщения отправятся позже» |
| `Connecting` | Идёт HTTP Upgrade | «Подключение…» |
| `Authenticating` | Отправлен `session.auth`, ответа нет | «Подключение…» |
| `Connected(sessionId, latencyMs)` | Получен `session.auth.ok` | Баннер скрыт |
| `Reconnecting(attempt, nextRetryInMs, reason)` | Обрыв, идёт backoff | «Переподключение… попытка N» |
| `Failed(error)` | Переподключение невозможно | «Нет соединения с сервером» |

Отдельно отслеживается фаза первичной синхронизации после подключения
(`SyncPhase`):

```
IDLE → AUTH → CHATS → MESSAGES → STORIES → WALLET → COMPLETE
                                                  ↘ FAILED
```

Фазы нужны, потому что offline-first клиент показывает данные из Room сразу,
а дельту с сервера добирает поэтапно. Пользователь видит прогресс вместо
пустого экрана с индикатором.

## Порядок доставки

Сервер **не обязан** гарантировать глобальный порядок событий, но обязан
гарантировать порядок внутри одного чата: сообщение, отправленное раньше,
не должно прийти позже. Практически это означает, что события одного чата
нельзя распределять по разным воркерам без синхронизации.

Клиент дополнительно защищён от перестановки: у каждого сообщения есть
`sent_at`, и список сортируется по нему, а не по порядку прихода кадров.

## Что нельзя делать серверу

- Отправлять кадры до `session.auth.ok` — кроме самого ответа на авторизацию.
- Закрывать соединение без кадра `session.kick` или кода `1008`, если причина
  в отзыве сессии: клиент уйдёт в бесконечный цикл переподключений.
- Игнорировать `session.ping` без ответа — через 50 секунд клиент разорвёт
  живое соединение.
- Рассылать события чатов, на которые клиент не подписан через
  `session.subscribe`: это кратный рост трафика на мобильной сети.
- Дублировать события при переподключении того же `device_id`.
