# 07. Ошибки

## Два канала, одна таксономия

Ошибки приходят двумя путями, но приводятся к одному набору доменных типов
`ScError` (`core/common/result/ScResult.kt`). Интерфейс работает с `ScError` и
не знает, откуда пришла ошибка — из HTTP-ответа или из кадра WebSocket.

| Канал | Носитель | Разбор на клиенте |
|---|---|---|
| REST | HTTP-статус + конверт в теле | `apiCall { }` → `HttpException.toScErrorFromHttp()` в `core/network/mapper/ApiCall.kt` |
| WebSocket | Кадр `error` или `ack` с `ok = false` | `SocketEventDecoder` → `SocketEvent.ServerError` |
| Локально | Исключение ввода-вывода, БД, шифрования | `Throwable.toScError()` в `:core:common` |

## Конверт ошибки REST

```json
{
  "error": {
    "code": "username_taken",
    "message": "Юзернейм уже занят",
    "field": "username",
    "retry_after_ms": 4200,
    "required": 2500,
    "available": 1250,
    "perk": "animated_avatar"
  }
}
```

Все поля, кроме `code`, необязательны. Клиент разбирает конверт с
`ignoreUnknownKeys = true`, поэтому сервер может добавлять поля без
согласования.

| Поле | Когда обязательно | Смысл |
|---|---|---|
| `code` | Всегда | Машинно-читаемый идентификатор, `snake_case` |
| `message` | Всегда | Готовая к показу строка на русском |
| `field` | При ошибке валидации | Имя поля формы, к которому относится ошибка |
| `retry_after_ms` | При `rate_limited` | Миллисекунды до повторной попытки |
| `required`, `available` | При `insufficient_funds` | Сколько нужно и сколько есть |
| `perk` | При `premium_required` | Какая именно возможность закрыта подпиской |

### `message` показывается пользователю дословно

Клиент не переписывает и не переводит `message` — он выводит его как есть.
Отсюда два требования:

1. Строка обязана быть на русском и понятной без контекста. «Ошибка 422» —
   не сообщение.
2. В ней не должно быть технических деталей: имён таблиц, стектрейсов,
   внутренних идентификаторов.

Если сервер не может сформулировать внятную строку, клиент подставит свою по
типу ошибки (`ScError` у каждого варианта имеет значение по умолчанию). Но это
запасной путь, а не норма: сообщение сервера точнее, потому что знает
конкретную причину.

### Ошибка при HTTP 200

Часть бизнес-исходов — не сбои, а нормальные ветки сценария. Покупка лота
отвечает `200 OK` со структурированным результатом, а не ошибкой:

```json
{ "status": "insufficient_funds", "required_silver": 2500, "available_silver": 1250 }
```

`status` принимает `success | insufficient_funds | taken | reserved`; любое
другое значение клиент трактует как запрет. Полный разбор — в
`core/network/mapper/DomainMappers.kt` → `BuyResponse.toDomain()`.

Правило: **HTTP-статус описывает состояние протокола, поле `status` в теле —
исход бизнес-операции.** Отвечать `402` на нехватку сильверов при покупке тоже
допустимо (клиент это обрабатывает), но тогда интерфейс не получит
`reserved_until` и не сможет показать, до какого момента лот удержан за
покупателем.

## Отображение HTTP-статуса в `ScError`

Таблица соответствует коду `toScErrorFromHttp()` и нормативна для сервера.

| Статус | `ScError` | Что делает интерфейс |
|---|---|---|
| `400` | `Validation(message, field)` | Подсвечивает поле формы |
| `401` | `Unauthorized` | Запускает обмен токенов; при неудаче — экран входа |
| `402` | `InsufficientFunds(required, available)` | Показывает нехватку и предлагает пополнить |
| `403` | `Forbidden(message, requiredPermission)` | Скрывает действие; `code` ошибки попадает в `requiredPermission` |
| `404`, `410` | `NotFound` | «Не найдено» с возможностью обновить |
| `409` | `Conflict` | Показывает конфликт и предлагает повторить с новыми данными |
| `413`, `415` | `Validation(message, field)` | Загрузку отклонил сервер: размер или тип файла |
| `422` | `Validation(message, field)` | Как `400` |
| `429` | `RateLimited(retryAfterMs)` | Обратный отсчёт до повторной попытки |
| `5xx` | `Server(message, code)` | «Ошибка сервера» с кнопкой повтора |
| Прочее | `Unknown` | Общий текст |

`402 Payment Required` использован осознанно: это единственный статус, чей
смысл буквально совпадает с «недостаточно средств». Клиент обрабатывает и его,
и бизнес-код `insufficient_funds`, поэтому сервер может выбрать любой из двух
способов.

### Бизнес-код важнее статуса

Код из конверта проверяется **до** классификации по статусу. Три кода клиент
распознаёт явно:

| `code` | Результат независимо от статуса |
|---|---|
| `insufficient_funds` | `ScError.InsufficientFunds(required, available)` |
| `premium_required` | `ScError.PremiumRequired(perk)` |
| `rate_limited` | `ScError.RateLimited(retry_after_ms)` |

Это нужно, потому что один и тот же статус может означать разное. `403` на
попытку установить анимированный аватар без подписки — это `premium_required`,
а `403` на попытку написать в закрытый канал — это действительно запрет. Без
кода интерфейс показал бы paywall там, где нужна просто блокировка действия.

### `Retry-After`

Заголовок измеряется в **секундах**, как требует RFC 9110. Отступать от этого
нельзя: заголовок выставляют не только наше приложение, но и балансировщики,
CDN и промежуточные прокси, и клиент не может угадывать, кто его добавил.

Миллисекундная точность передаётся в теле (`retry_after_ms`). Заголовок
используется как запасной вариант, когда тело отсутствует или не разобрано.

Значение-дата (`Retry-After: Wed, 21 Oct 2026 07:28:00 GMT`) не
поддерживается: клиент вернёт «нет обратного отсчёта» и просто позволит
повторить попытку.

## Ошибки WebSocket

### Кадр `error`

```json
{ "v": 1, "id": "<id команды>", "op": "error", "ts": 1730000000000,
  "payload": { "code": "chat_not_found", "message": "Чат не найден", "retryable": false } }
```

`id` обязан совпадать с идентификатором команды, иначе клиент не поймёт, к
чему относится отказ, и корутина в `sendAndAwait` будет ждать до таймаута.

`retryable` управляет поведением: при `true` клиент может повторить команду
после переподключения (она остаётся в `OutgoingQueue`), при `false` — обязан
сдать команду и показать ошибку.

### Кадр `ack` с отказом

```json
{ "v": 1, "id": "<id команды>", "op": "ack", "ts": 0,
  "payload": { "op": "message.send", "ok": false } }
```

`ack` с `ok = false` без подробностей — крайний случай. Предпочтительнее
полноценный кадр `error`: «не получилось» без причины не позволяет ни
повторить правильно, ни объяснить пользователю.

### Коды, влияющие на сессию

| `code` | Действие клиента |
|---|---|
| `protocol_version_unsupported` | Переподключение бессмысленно; нужен релиз с новой версией |
| `token_expired` | Обмен токенов через REST, затем новое рукопожатие |
| `session_revoked` | Выход из аккаунта |

Отзыв сессии дополнительно передаётся кадром `session.kick` — см.
[03-websocket.md](03-websocket.md).

## Таксономия `ScError` и поведение интерфейса

| Вариант | Причина | Показывать пользователю |
|---|---|---|
| `Network(message, retryAfterMs)` | Нет связи, таймаут, DNS | Да, с кнопкой повтора |
| `Unauthorized` | `401`, протух refresh-токен | Нет — сразу переход на экран входа |
| `Forbidden(message, requiredPermission)` | `403` | Да, но действие скрывается |
| `NotFound` | `404`, `410` | Да |
| `Conflict` | `409` | Да |
| `Validation(message, field)` | `400`, `422`, локальная проверка | Да, у конкретного поля |
| `RateLimited(message, retryAfterMs)` | `429` | Да, с обратным отсчётом |
| `InsufficientFunds(required, available)` | `402` или бизнес-код | Да, с суммами |
| `PremiumRequired(perk)` | Бизнес-код | Да — открывает paywall |
| `Server(message, code)` | `5xx` | Да, без технических деталей |
| `Local(message)` | БД, шифрование, файловая система | Да, обобщённо |
| `Canceled` | Пользователь отменил операцию | **Никогда** |
| `Unknown(message)` | Всё остальное | Да, обобщённо |

### `Canceled` — не ошибка

Отмена выбора файла, отмена съёмки, отмена отправки свайпом — нормальный
исход. Показывать «Ошибка: операция отменена» после того, как пользователь
сам нажал «Отмена», значит сообщать ему о собственной осмысленной операции как
о сбое. Все обработчики обязаны проверять этот случай первыми.

### Отмена корутины не превращается в ошибку

`apiCall` и `scResult` пробрасывают `CancellationException`, а не
оборачивают его. Проглотить отмену — значит сломать structured concurrency:
родительская корутина перестанет понимать, что дочерняя завершена, и
`viewModelScope` не сможет корректно отменять работу при уходе с экрана.

## Словарь кодов ошибок

Коды ниже нормативны: клиент распознаёт часть из них явно, остальные
обрабатывает по статусу. Сервер может добавлять новые — неизвестный код не
ломает клиент, он просто классифицируется по HTTP-статусу.

### Авторизация

| Код | Статус | Смысл |
|---|---|---|
| `phone_invalid` | 422 | Номер не в формате E.164 |
| `otp_invalid` | 400 | Неверный код |
| `otp_expired` | 400 | Срок действия кода истёк |
| `otp_attempts_exceeded` | 429 | Превышено число попыток ввода |
| `otp_send_limited` | 429 | Превышен лимит отправок на номер |
| `token_expired` | 401 | Access-токен истёк |
| `refresh_invalid` | 401 | Refresh-токен отозван или уже использован |
| `session_revoked` | 401 | Сессия завершена сервером |
| `account_banned` | 403 | Аккаунт заблокирован |

### Профиль и чаты

| Код | Статус | Смысл |
|---|---|---|
| `username_taken` | 409 | Юзернейм занят |
| `username_reserved` | 403 | Юзернейм зарезервирован администрацией |
| `username_invalid` | 422 | Не соответствует правилам |
| `user_not_found` | 404 | Пользователь не существует |
| `chat_not_found` | 404 | Чат не существует или недоступен |
| `not_a_member` | 403 | Пользователь не участник чата |
| `permission_denied` | 403 | Роль не позволяет действие |
| `member_limit_reached` | 409 | Превышен `max_group_members` |
| `user_blocked` | 403 | Пользователь в чёрном списке |
| `slow_mode_active` | 429 | Действует режим медленной отправки |
| `invite_invalid` | 404 | Ссылка недействительна |
| `invite_limit_reached` | 409 | Исчерпано число использований ссылки |

### Сообщения и медиа

| Код | Статус | Смысл |
|---|---|---|
| `message_too_long` | 422 | Превышен `max_message_length` |
| `message_not_found` | 404 | Сообщение удалено |
| `edit_window_closed` | 403 | Время на редактирование истекло |
| `content_protected` | 403 | Контент защищён от пересылки |
| `upload_too_large` | 413 | Превышен `max_upload_mb` |
| `upload_ticket_expired` | 410 | Подписанный URL протух |
| `mime_not_allowed` | 415 | Тип файла не принимается |
| `poll_closed` | 409 | Голосование завершено |

### Экономика

| Код | Статус | Смысл |
|---|---|---|
| `insufficient_funds` | 402 | Не хватает сильверов |
| `listing_not_available` | 409 | Лот снят с продажи |
| `listing_reserved` | 409 | Лот удержан за другим покупателем |
| `own_listing` | 403 | Нельзя купить собственный лот |
| `offer_too_low` | 422 | Оффер ниже `min_offer_silver` |
| `transfer_to_self` | 422 | Перевод самому себе |
| `streak_already_claimed` | 409 | Награда за сегодня получена |
| `gift_not_owned` | 403 | Подарок не принадлежит пользователю |
| `gift_not_convertible` | 422 | Подарок нельзя обменять на сильверы |
| `idempotency_conflict` | 409 | Тот же `Idempotency-Key` пришёл с другим телом |
| `missing_idempotency_key` | 400 | На денежной операции нет заголовка `Idempotency-Key` |

Оба последних кода клиент распознаёт **по статусу**, а не по строке кода:
`409` даёт `ScError.Conflict`, `400` — `ScError.Validation`. Специальной ветки
в интерфейсе они не требуют — это ошибки контракта между клиентом и сервером,
а не состояния, которые нужно объяснять пользователю. Нормативное описание
заголовка и списка операций — в [02-rest-api.md](02-rest-api.md), раздел
«Идемпотентность».

|---|---|---|
